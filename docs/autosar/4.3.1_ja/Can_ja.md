## 7 機能仕様

L-PDU の送信では、Can モジュールは、CAN コントローラのハードウェアの中の適切なバッファへ、L-PDU を書き込む。L-PDU の送信の詳細は、7.5 章を参照。

L-PDU の受信では、Can モジュールは、ID、DLC、L-SDU へのポインタをパラメータとして、受信通知のコールバック関数を呼ぶ。L-PDU の受信の詳細は、7.6 章を参照。

Can モジュールは、周期処理関数として働くインタフェースを提供し、これは、Basic Software Scheduler モジュールにより周期的に呼ばれなければならない。さらに、Can モジュールは、CAN コントローラの状態を制御するサービスを提供する。バスオフとウェイクアップのイベントは、コールバック関数で通知される。

Can モジュールは、ハードウェアリソースへアクセスする基本ソフトウェアモジュールである。したがって、AUTOSAR_SRS_SPAL（[3] を参照）で規定された、基本ソフトウェアモジュールの要求を満たすように設計される。

**[SWS_Can_00033]** Can モジュールは、必要なすべての CAN ハードウェアユニットの割り込みについて、割り込みサービスルーチンを実装しなければならない。（SRS_BSW_00164、SRS_SPAL_12129）

**[SWS_Can_00419]** Can モジュールは、CAN コントローラの、使われないすべての割り込みを無効にしなければならない。

**[SWS_Can_00420]** Can モジュールは、（ハードウェアにより自動的に行われない場合）ISR の最後で、割り込みフラグをリセットしなければならない。

実装のヒント: Can モジュールは、ベクタテーブルのエントリの設定（すなわち、優先度）を設定してはならない。

**[SWS_Can_00079]** Can モジュールは、[11] に記述された、すべての設計と実装のガイドラインを満たさなければならない。（SRS_BSW_00007、SRS_BSW_00306、SRS_BSW_00308、SRS_BSW_00309、SRS_BSW_00330）

### 7.1 ドライバの範囲

1 つの Can モジュールは、複数の CAN コントローラから成りうる、1 つの CAN ハードウェアユニットへのアクセスを提供する。

**[SWS_Can_00077]** 異なる種類の CAN ハードウェアユニットには、異なる Can モジュールを実装しなければならない。（SRS_BSW_00347）

**[SWS_Can_00284]** 複数の CAN ハードウェアユニット（同じまたは異なるベンダの）が 1 つの ECU に実装される場合、Can モジュールの関数名とグローバル変数は、同じ名前の関数が 2 つ生成されないように実装されなければならない。

命名規則は次のとおりである。

`<Can モジュール名>_<ベンダ ID>_<ベンダ固有の API 名><ドライバの略称>()`

SRS_BSW_00347 が、命名規則を規定している。

**[SWS_Can_00385]** 命名規則は、1 つの ECU で、複数の異なる CAN コントローラの種類をサポートしなければならない場合にだけ、使わなければならない。

**[SWS_Can_00386]** 1 つのコントローラの種類だけが使われる場合、`<ドライバの略称>` の拡張なしの、元の命名規則で十分である。

複数の Can モジュールが CanIf モジュールでどのように扱われるかの説明は、[5] を参照。

### 7.2 ドライバの状態機械

Can モジュールは、`CAN_UNINIT` と `CAN_READY` の 2 つの状態を持つ、非常に単純な状態機械を持つ。図 7.1 に状態機械を示す。

**[SWS_Can_00103]** 電源投入／リセットの後、Can モジュールは、状態 `CAN_UNINIT` でなければならない。（SRS_BSW_00406）

> （図 7-1「ドライバの状態機械」: 状態機械図。訳なし。読み取れる内容: `CAN_UNINIT` から `Can_Init` で `CAN_READY` へ。）

**[SWS_Can_00246]** 関数 `Can_Init` は、HW ユニットの中のすべてのコントローラを初期化した後に、モジュールの状態を `CAN_READY` に変更しなければならない。（SRS_SPAL_12057、SRS_Can_01041）

**[SWS_Can_00245]** 関数 `Can_Init` は、すべての CAN コントローラを、そのコンフィギュレーションに従って初期化しなければならない。（SRS_SPAL_12057、SRS_Can_01041）

各 CAN コントローラは、その後、関数 `Can_SetControllerMode(CAN_T_START)` を呼んで、別々に開始されなければならない。

実装のヒント: HW ユニットの中のすべての CAN コントローラに影響するハードウェアのレジスタ設定は、関数 `Can_Init` の中でだけ設定できる。

実装のヒント: ECU State Manager モジュールは、実行時に、`Can_Init` を多くても 1 回だけ呼ぶものとする。

### 7.3 CAN コントローラの状態機械

各 CAN コントローラは、ハードウェアで実装された、複雑な状態機械を持つ。この説明では、簡単のために、状態の数を、`UNINIT`、`STOPPED`、`STARTED`、`SLEEP` の 4 つの基本的な状態に減らしている。

各 CAN コントローラについて、対応する「ソフトウェア」の状態機械が、CanIf モジュール [5] に、次の状態で実装される: `CANIF_CS_UNINIT`、`CANIF_CS_STOPPED`、`CANIF_CS_STARTED`、`CANIF_CS_SLEEP`。ソフトウェアの状態機械の実装は、[5] に示されている。CAN ハードウェアへのアクセスは、Can モジュールの関数に、すべて隠蔽されるが、Can モジュールは、状態の変更を記憶しない。

遷移の段階の間、CanIf モジュールの中のソフトウェアのコントローラの状態は、CAN コントローラのハードウェアの状態と異なることがある。

Can モジュールは、サービス `Can_Init`、`Can_SetBaudrate`、`Can_SetControllerMode` を提供する。これらのサービスは、ハードウェアの CAN コントローラの状態の、必要な変更を起こす、必要なレジスタ設定を行う。

外部のイベントによる状態変更を起動する可能性は、2 つある。

- バスオフのイベント
- HW のウェイクアップのイベント

これらのイベントは、割り込み、または `Can_MainFunction_BusOff` や `Can_MainFunction_Wakeup` でポーリングされるステータスビットのいずれかで通知される。

Can モジュールは、必要な動作（すなわち、バスオフの場合のハードウェアによる回復なし）を満たすために必要な、レジスタ設定を行う。その後、対応するコールバック関数で CanIf モジュールへ通知する。ソフトウェアの状態は、そのコールバック関数の中で変更される。

Can モジュールは、状態変更の有効性を検査しない。現在の状態で許される遷移だけを起動するのは、上位層のモジュールの役割である。開発エラーが有効な場合、Can モジュールは、遷移を検査する。上位層のモジュールの実装が誤っていた場合、Can モジュールは、開発エラー `CAN_E_TRANSITION` を発生させる。

Can モジュールは、`Can_Write` を実行する前、またはコールバックを発生させる前に、実際の状態を検査しない。

遷移の段階の間（CanIf モジュールの中のソフトウェアのコントローラの状態が、CAN コントローラのハードウェアの状態と異なる間）は、ハードウェアの CAN コントローラがまだバスに参加していないため、送信が失敗するか、遅れることがある。Can モジュールは、この場合の通知を提供しない。

#### 7.3.1 CAN コントローラの状態の説明

この章は、異なるソフトウェアの状態について、必要なハードウェアの動作を説明する。ソフトウェアの状態機械自体は、CanIf モジュールに実装され、説明されている。状態図は [5] を参照。

**CAN コントローラの状態 UNINIT**: CAN コントローラは初期化されていない。CAN モジュールに属するすべてのレジスタは、リセットの状態で、CAN の割り込みは無効である。CAN コントローラは、CAN バスに参加していない。

**CAN コントローラの状態 STOPPED**: この状態では、CAN コントローラは初期化されているが、バスに参加していない。さらに、エラーフレームとアクノレッジを送ってはならない。（例: 多くのコントローラでは、「初期化」モードに入ると、コントローラが停止する。）

**CAN コントローラの状態 STARTED**: コントローラは、完全な機能を持つ通常の動作モードにあり、ネットワークに参加することを意味する。多くのコントローラでは、「初期化」モードを出ると、コントローラが開始する。

**CAN コントローラの状態 SLEEP**: ハードウェアの設定は、スリープモードをサポートする CAN ハードウェア（CAN ハードウェアが CAN バスを介したウェイクアップを直接サポートする）の場合に限り、状態 `STOPPED` と異なる。

**[SWS_Can_00257]** CAN ハードウェアがスリープモードをサポートし、`SLEEP` の状態への遷移を起動されたとき、Can モジュールは、ハードウェアが CAN バスを介して起こせる `SLEEP` の状態に、コントローラを設定しなければならない。（SRS_SPAL_12067）

**[SWS_Can_00258]** CAN ハードウェアがスリープモードをサポートせず、`SLEEP` の状態への遷移を起動されたとき、Can モジュールは、ソフトウェアにより状態 `STOPPED` への遷移を起動されたときにだけ戻る、論理的な `SLEEP` の状態を、エミュレートしなければならない。

**[SWS_Can_00404]** CAN ハードウェアは、論理的な `SLEEP` の状態が有効な間、状態 `STOPPED` のままでなければならない。

#### 7.3.2 CAN コントローラの状態遷移

状態遷移は、必要な遷移をパラメータとして、関数 `Can_SetControllerMode` により、ソフトウェアで起動される。ソフトウェアで起動された状態遷移の成功は、コールバック関数（`CanIf_ControllerModeIndication`）で通知される。要求された状態に達したかの監視は、上位層のモジュールの一部であり、Can モジュールの一部ではない。

一部の遷移は、バス（ハードウェア）のイベントで起動される。これらの遷移は、コールバック関数（`CanIf_ControllerBusOff`、`EcuM_CheckWakeup`）による通知を引き起こす。

状態遷移の妥当性の検査は、開発エラーの検出をオンにした場合にだけ行われる。製品のコードでの、無効な遷移の動作は、未定義である。図 7-2 は、有効なすべての状態遷移を示す。

> （図 7-2「CAN コントローラの状態遷移」: 状態機械図。訳なし。読み取れる内容: `UNINIT` → `STOPPED`（`Can_Init`）、`STOPPED` ⇄ `STARTED`（`CAN_T_START` / `CAN_T_STOP`。バスオフでも `STARTED` → `STOPPED`）、`STOPPED` ⇄ `SLEEP`（`CAN_T_SLEEP` / `CAN_T_WAKEUP`。ハードウェアのウェイクアップでも `SLEEP` → `STOPPED`）。）

#### 7.3.3 関数 `Can_Init` による状態遷移

- `UNINIT` → `STOPPED`（HW ユニットのすべてのコントローラについて）
- 関数呼び出し `Can_Init` によるソフトウェアでの起動
- HW ユニットの中のすべての CAN コントローラの設定を行う

すべての制御レジスタは、静的なコンフィギュレーションに従って設定される。

**[SWS_Can_00259]** 関数 `Can_Init` は、すべての CAN コントローラを状態 `STOPPED` に設定しなければならない。

関数 `Can_Init` が呼ばれたときに、Can モジュールが `CAN_UNINIT` の状態でない場合、または CAN コントローラが `UNINIT` の状態でない場合、エラー `CAN_E_TRANSITION` を発生させなければならない（[SWS_Can_00174] と [SWS_Can_00408] を参照）。

#### 7.3.4 関数 `Can_SetBaudrate` による状態遷移

- `STOPPED` → `STOPPED`、`SLEEP` → `SLEEP`、`STARTED` → `STARTED`
- 関数呼び出し `Can_SetBaudrate` によるソフトウェアでの起動
- CAN コントローラのコンフィギュレーションを変更する

CAN コントローラのレジスタは、静的なコンフィギュレーションに従って設定される。

**[SWS_Can_00256]** `Can_SetBaudrate` の呼び出しが CAN コントローラの再初期化を引き起こす場合: 関数 `Can_SetBaudrate` は、コントローラが状態 `STOPPED` でなければ `E_NOT_OK` を返し、Can モジュールの開発エラーの検出が有効なら、エラー `CAN_E_TRANSITION` を発生させなければならない。

**[SWS_Can_00260]** 再初期化が必要な場合、関数 `Can_SetBaudrate` は、CAN コントローラを状態 `STOPPED` に保たなければならない。

**[SWS_Can_00422]** 再初期化が必要な場合、関数 `Can_SetBaudrate` は、CAN コントローラがネットワークに参加することになる設定が、設定されないことを保証しなければならない。

#### 7.3.5 関数 `Can_SetControllerMode` による状態遷移

ソフトウェアは、関数 `Can_SetControllerMode` で、CAN コントローラの状態遷移を起動できる。CAN ハードウェアによっては、新しい CAN コントローラの状態へ遷移するためのレジスタ設定の変更が、遅れてから有効になることがある。Can モジュールは、状態遷移の成功の後、新しい状態について上位層へ通知する（`CanIf_ControllerModeIndication`）。要求された状態に達したかの監視は、上位層のモジュールの一部であり、Can モジュールの一部ではない。

**[SWS_Can_00370]** 関数 `Can_Mainfunction_Mode` は、変更が有効になったことを示すフラグが立つまで、CAN のステータスレジスタのフラグをポーリングし、関数 `CanIf_ControllerModeIndication` で、状態遷移の成功を上位層へ通知しなければならない。

**[SWS_Can_00371]** このポーリングは、ブロックする関数について最大で `CanTimeoutDuration` の時間かかり、したがって、ポーリングの時間は制限される。（SRS_SPAL_12077）

**[SWS_Can_00398]** 関数 `Can_SetControllerMode` は、ブロックする関数を避けるために、タイムアウトの監視にシステムサービス `GetCounterValue` を使わなければならない。

**[SWS_Can_00372]** フラグが、変更が効果を持たないことを示し、最大時間 `CanTimeoutDuration` が経過した場合、関数 `Can_SetControllerMode` は抜けなければならず、関数 `Can_Mainfunction_Mode` は、フラグのポーリングを続けなければならない。（SRS_SPAL_12077）

**[SWS_Can_00373]** 状態遷移が関数 `Can_SetControllerMode` で起動された場合、関数 `Can_Mainfunction_Mode` は、CAN コントローラの状態遷移の成功を上位層へ通知するために、関数 `CanIf_ControllerModeIndication` を呼ばなければならない。

**関数 `Can_SetControllerMode(CAN_T_START)` による状態遷移: `STOPPED` → `STARTED`（ソフトウェアで起動）**

**[SWS_Can_00261]** 関数 `Can_SetControllerMode(CAN_T_START)` は、CAN コントローラがネットワークに参加するように、ハードウェアのレジスタを設定しなければならない。

**[SWS_Can_00262]** 関数 `Can_SetControllerMode(CAN_T_START)` は、CAN コントローラが完全に動作可能になるまで、限られた時間待たなければならない。[SWS_Can_00371] を参照。

CAN コントローラが動作可能になる前に開始された送信要求は、失われる。動作可能であることの唯一の指標は、TX 確認または RX 通知の受信である。送信側のエンティティは、確認のタイムアウトを受け取りうるため、それに対処できる必要がある。

**[SWS_Can_00409]** 関数 `Can_SetControllerMode(CAN_T_START)` が呼ばれたときに、CAN コントローラが状態 `STOPPED` でない場合、無効な状態遷移を検出しなければならない（[SWS_Can_00200] を参照）。

**関数 `Can_SetControllerMode(CAN_T_STOP)` による状態遷移: `STARTED` → `STOPPED`（ソフトウェアで起動）**

**[SWS_Can_00263]** 関数 `Can_SetControllerMode(CAN_T_STOP)` は、CAN コントローラがネットワークへの参加を止めるように、CAN ハードウェアの中のビットを設定しなければならない。

**[SWS_Can_00264]** 関数 `Can_SetControllerMode(CAN_T_STOP)` は、CAN コントローラが本当に切られるまで、限られた時間待たなければならない。[SWS_Can_00371] を参照。

**[SWS_Can_00282]** 関数 `Can_SetControllerMode(CAN_T_STOP)` は、保留中のメッセージをキャンセルしなければならない。

**[SWS_Can_00283]** 関数 `Can_SetControllerMode(CAN_T_STOP)` は、キャンセルの通知を呼んではならない。

ヒント: 保留中のメッセージが `Can_SetControllerMode(CAN_T_STOP)` でキャンセルされる場合でも、ハードウェアの制限と競合の問題がある。したがって、キャンセルされたメッセージが、ハードウェアによりまだ処理されるかどうかは、保証できない。

**[SWS_Can_00410]** 関数 `Can_SetControllerMode(CAN_T_STOP)` が呼ばれたときに、CAN コントローラが状態 `STARTED` でも状態 `STOPPED` でもない場合、無効な状態遷移を検出しなければならない（[SWS_Can_00200] を参照）。

**関数 `Can_SetControllerMode(CAN_T_SLEEP)` による状態遷移: `STOPPED` → `SLEEP`（ソフトウェアで起動）**

**[SWS_Can_00265]** 関数 `Can_SetControllerMode(CAN_T_SLEEP)` は、コントローラをスリープモードに設定しなければならない。

**[SWS_Can_00266]** CAN HW がスリープモードをサポートする場合、関数 `Can_SetControllerMode(CAN_T_SLEEP)` は、CAN コントローラが `SLEEP` の状態になり、CAN ハードウェアが起こせることが確実になるまで、限られた時間待たなければならない。[SWS_Can_00371] を参照。

**[SWS_Can_00290]** CAN HW がスリープモードをサポートしない場合、関数 `Can_SetControllerMode(CAN_T_SLEEP)` は、CAN コントローラを論理的なスリープモードに設定しなければならない。

**[SWS_Can_00405]** この論理的なスリープモードは、関数 `Can_SetControllerMode(CAN_T_WAKEUP)` が呼ばれた場合にだけ、抜けなければならない。

**[SWS_Can_00411]** 関数 `Can_SetControllerMode(CAN_T_SLEEP)` が呼ばれたときに、CAN コントローラが状態 `STOPPED` でも状態 `SLEEP` でもない場合、無効な状態遷移を検出しなければならない（[SWS_Can_00200] を参照）。

**関数 `Can_SetControllerMode(CAN_T_WAKEUP)` による状態遷移: `SLEEP` → `STOPPED`（ソフトウェアで起動）**

**[SWS_Can_00267]** CAN HW がスリープモードをサポートしない場合、関数 `Can_SetControllerMode(CAN_T_WAKEUP)` は、論理的なスリープモードから戻らなければならないが、CAN コントローラの状態には影響を持たない（コントローラはすでに停止の状態であるため）。

**[SWS_Can_00268]** 関数 `Can_SetControllerMode(CAN_T_WAKEUP)` は、CAN コントローラが状態 `STOPPED` になるまで、限られた時間待たなければならない。[SWS_Can_00371] を参照。

**[SWS_Can_00412]** 関数 `Can_SetControllerMode(CAN_T_WAKEUP)` が呼ばれたときに、CAN コントローラが状態 `SLEEP` でも状態 `STOPPED` でもない場合、無効な状態遷移を検出しなければならない（[SWS_Can_00200] を参照）。

#### 7.3.6 ハードウェアのイベントによる状態遷移

**ハードウェアのウェイクアップ（CAN バスからのウェイクアップのイベントで起動）による状態遷移: `SLEEP` → `STOPPED`**

- 入ってくる L-PDU により起動される。
- ECU State Manager モジュールが、関数 `EcuM_CheckWakeup` で通知される。

この状態遷移は、スリープモードがハードウェアでサポートされている場合にだけ起こる。

**[SWS_Can_00270]** ハードウェアのウェイクアップ（CAN バスからのウェイクアップのイベントで起動）で、CAN コントローラは、状態 `STOPPED` へ遷移しなければならない。

**[SWS_Can_00271]** ハードウェアのウェイクアップ（CAN バスからのウェイクアップのイベントで起動）で、Can モジュールは、割り込みのコンテキスト、または `Can_MainFunction_Wakeup` のコンテキストのいずれかで、関数 `EcuM_CheckWakeup` を呼ばなければならない。（SRS_BSW_00375、SRS_SPAL_12069、SRS_Can_01054）

**[SWS_Can_00269]** Can モジュールは、ウェイクアップを引き起こした L-PDU を、それ以上処理してはならない。

**[SWS_Can_00048]** スリープ遷移の間に CAN バスのウェイクアップが起きた場合、関数 `Can_SetControllerMode(CAN_T_WAKEUP)` は、`CAN_NOT_OK` を返さなければならない。（SRS_Can_01122）

**バスオフ（CAN コントローラの状態変化で起動）による状態遷移**

**[SWS_Can_00020]** `STARTED` → `STOPPED`: CAN コントローラがバスオフの状態に達した場合に、ハードウェアにより起動される。CanIf モジュールは、状態 `STOPPED` に達した後、関数 `CanIf_ControllerBusOff` で通知される。（SRS_Can_01055）

**[SWS_Can_00272]** バスオフの検出の後、CAN コントローラは、状態 `STOPPED` へ遷移しなければならず、Can モジュールは、CAN コントローラがネットワークにもう参加していないことを保証しなければならない。（SRS_Can_01060）

**[SWS_Can_00273]** バスオフの検出の後、Can モジュールは、まだ保留中のメッセージを、キャンセルの通知を発生させずに、キャンセルしなければならない。（SRS_Can_01060）

**[SWS_Can_00274]** Can モジュールは、自動的なバスオフからの回復を、無効にするか、抑制しなければならない。（SRS_Can_01060）

### 7.4 Can モジュール／コントローラの初期化

ECU State Manager モジュールは、起動の段階で、Can モジュールの他の関数を使う前に、関数 `Can_Init` を呼んで、Can モジュールを初期化しなければならない。

**[SWS_Can_00250]** 関数 `Can_Init` は、次のものを初期化しなければならない。

- 静的変数（フラグを含む）
- CAN HW ユニット全体の共通の設定
- 各 CAN コントローラの CAN コントローラ固有の設定

（SRS_BSW_00101）

**[SWS_Can_00053]** `Can_Init` は、使われない CAN コントローラのハードウェアリソースのレジスタを、変更してはならない。（SRS_SPAL_12125）

Can モジュールは、コントローラのレジスタの初期化について、次の規則を適用しなければならない。

- **[SWS_Can_00407]** レジスタの用途が 1 つだけに限られるハードウェアの場合、その機能を実装する Can モジュールが、レジスタの初期化に責任を持つ。
- レジスタが複数のハードウェアモジュールに影響しうる I/O レジスタの場合、それは PORT ドライバにより初期化されなければならない。
- レジスタが複数のハードウェアモジュールに影響しうるが、I/O レジスタでない場合、それは MCU ドライバにより初期化されなければならない。
- リセット直後の初期化が必要な、1 回だけ書き込めるレジスタは、スタートアップコードにより初期化されなければならない。
- その他のレジスタはすべて、スタートアップコードにより初期化されなければならない。

（SRS_SPAL_12461）

**[SWS_Can_00056]** 第 10 章で「多重（multiple）」（`M` または `x`）と印が付いたポストビルドのコンフィギュレーションの要素は、モジュールの初期化関数へポインタ `Config` を渡すことで、選択できる。

**[SWS_Can_00062]** 再初期化が必要な場合、関数 `Can_SetBaudrate` は、CAN コントローラとコントローラ固有の設定を再初期化しなければならない。（SRS_Can_01139、SRS_Can_01042）

再初期化が必要な場合、`Can_SetBaudrate` を呼ぶ前に、CanIf モジュールが、まず CAN コントローラを状態 `STOPPED` に設定しなければならない。

**[SWS_Can_00255]** 関数 `Can_SetBaudrate` は、単一の CAN コントローラの特定のコンフィギュレーションを含むレジスタ領域にだけ、影響しなければならない。

**[SWS_Can_00021]** 希望する CAN コントローラのコンフィギュレーションは、パラメータ `Config` で選択できる。（SRS_BSW_00344、SRS_BSW_00404、SRS_BSW_00405、SRS_SPAL_12263、SRS_SPAL_12265）

**[SWS_Can_00291]** `Config` は、ROM に保存された、実装固有のデータ構造の配列へのポインタである。異なるコントローラのコンフィギュレーションセットは、ROM にデータ構造として置かれる。（SRS_BSW_00438）

`Config` の取りうる値は、コンフィギュレーションの記述（第 10 章を参照）で与えられる。Can モジュールのコンフィギュレーションは、グローバルな CAN HW ユニットの設定と、デフォルトの CAN コントローラのコンフィギュレーションセットへの参照を定義する。

### 7.5 L-PDU の送信

L-PDU の送信では、Can モジュールは、L-PDU の内容の ID と DLC を、（必要であれば）ハードウェア固有の形式に変換し、送信を起動する。

**[SWS_Can_00059]** CAN によるメモリへのデータの割り当ては、最初に送り出される CAN データバイトが配列の要素 0、最後に送り出される CAN データバイトが配列の要素 7 になるように定義される。（SRS_SPAL_12063）

**[SWS_Can_00427]** CAN ハードウェアバッファの中の表現が AUTOSAR の定義と異なる場合、Can モジュールは、上位層のために、適合させた SDU バッファを提供しなければならない。

**[SWS_Can_00100]** 一意の HTH を持つ複数の TX ハードウェアオブジェクトを、コンフィギュレーションしてよい。CanIf モジュールは、TX 要求のパラメータとして HTH を提供する。取りうるコンフィギュレーションは、図 7-3 を参照。（SRS_Can_01135）

> （図 7-3「HTH と HRH のハードウェアオブジェクトへの割り当ての例」: 図。訳なし。読み取れる内容: CAN ハードウェアのメッセージオブジェクト（ID、DLC、SDU）に、HRH = 0、1、2、3 と HTH = 4、5 が割り当てられ、未使用のものもある。HTH と HRH の番号付けは実装固有で、選ばれた番号付けは例にすぎない。）

**[SWS_Can_00276]** 関数 `Can_Write` は、パラメータ `PduInfo` の中で渡された `swPduHandle` を、Can モジュールがこの要求について、`swPduHandle` をパラメータとして `CanIf_TxConfirmation` を呼ぶまで、保存しなければならない。

[SWS_Can_00276] の機能は、CanIf モジュールの実装の中での探索の時間を減らすために使われる。

**[SWS_Can_00016]** Can モジュールは、送信の成功を示すために、`CanIf_TxConfirmation` を呼ばなければならない。これは、対応する HW リソースの TX 割り込みサービスルーチンにより、またはポーリングモードの場合は `Can_MainFunction_Write` の中で呼ばれなければならない。（SRS_Can_01051）

#### 7.5.1 優先度の逆転

優先度の逆転を防ぐために、2 つの仕組みが必要である。多重化された送信と、ハードウェアによるキャンセルである（2.1 章を参照）。

##### 7.5.1.1 多重化された送信

**[SWS_Can_00277]** Can モジュールは、機能「多重化された送信」が、プリコンパイル時に、静的にコンフィギュレーションできる（ON | OFF）ようにしなければならない。（SRS_Can_01134）

**[SWS_Can_00401]** 複数の送信ハードウェアオブジェクト（`CanHwObjectCount` で定義される）は、上位層へ 1 つの送信エンティティを表すために、1 つの HTH により割り当てられなければならない。（SRS_Can_01134）

**[SWS_Can_00402]** Can モジュールは、次のいずれかのデバイスについて、多重化された送信の仕組みをサポートしなければならない。

- 送信エンティティにグループ化された、複数の送信ハードウェアオブジェクトが、同じレジスタセットを介して埋められ、マイクロコントローラが、L-PDU を空いているバッファへ自律的に保存する。
- ハードウェアが、送信エンティティの中の空いている送信ハードウェアオブジェクトを識別するための、レジスタまたは関数を提供する。

（SRS_Can_01134）

**[SWS_Can_00403]** Can モジュールは、L-PDU の優先度の順に L-PDU を送るデバイスについて、多重化された送信をサポートしなければならない。（SRS_Can_01134）

注: 優先度の扱いのソフトウェアによるエミュレーションは、そのオーバーヘッドが、多重化された送信の利点を失わせるため、避けるべきである。

> （図 7-4「多重化された送信での、HTH と HRH のハードウェアオブジェクトへの割り当ての例」: 図。訳なし。HTH と HRH の番号付けは実装固有で、選ばれた番号付けは例にすぎない。）

##### 7.5.1.2 送信のキャンセル

一部のアプリケーションでは、常に最新のデータをバスで送信することが求められる。前の送信周期から、送信バッファで保留されている L-PDU は、現在の送信周期の L-PDU で置き換えられなければならない。この要求は、同一の優先度の保留中の L-PDU のキャンセルによりサポートされる。ただし、同一の優先度の L-PDU のキャンセルと置き換えは、優先度の逆転につながりうる。これは、優先度の逆転を防ぐ要求と矛盾する。両方の要求を満たすために、コンフィギュレーションパラメータ `CanIdenticalIdCancellation` が、同一の優先度の L-PDU のキャンセルを、有効／無効にする。

**[SWS_Can_00278]** Can モジュールは、機能「送信のキャンセル」が、プリコンパイル時に、静的にコンフィギュレーションできる（ON | OFF）ようにしなければならない。（SRS_Can_01133）

完全なキャンセルのシーケンスは、CanIf モジュール [5] に記述されている。

**[SWS_Can_00432]** Can モジュールは、同一の優先度の保留中の L-PDU のキャンセルが、パラメータ `CanIdenticalIdCancellation` により、プリコンパイル時に、静的にコンフィギュレーションできるようにしなければならない。

**[SWS_Can_00285]** 送信のキャンセルは、CanIf モジュールの中で送信バッファが有効な場合に限り、使ってよい。（SRS_Can_01133）

**[SWS_Can_00286]** HTH により割り当てられた送信ハードウェアオブジェクトが使用中で、より高い優先度の L-PDU の送信が要求された場合、Can モジュールは、キャンセルを開始しなければならない。（SRS_Can_01133）

**[SWS_Can_00433]** HTH により割り当てられた送信ハードウェアオブジェクトが使用中で、同一の優先度の L-PDU の送信が要求され、`CanIdenticalIdCancellation` が有効な場合、Can モジュールは、キャンセルを開始しなければならない。

次の 2 つの項目は、多重化された送信の機能が有効で、複数の送信ハードウェアオブジェクトが 1 つの HTH により割り当てられている場合に有効である。

**[SWS_Can_00399]** HTH により割り当てられたすべての送信ハードウェアオブジェクトが使用中で、より高い優先度の L-PDU の送信が要求された場合、Can モジュールは、最も低い優先度の L-PDU のキャンセルを開始しなければならない。（SRS_Can_01133）

**[SWS_Can_00400]** HTH により割り当てられた送信ハードウェアオブジェクトの 1 つが使用中で、同一の優先度の L-PDU の送信が要求され、`CanIdenticalIdCancellation` が有効な場合、Can モジュールは、キャンセルを開始しなければならない。（SRS_Can_01133）

入ってきた要求も、キャンセルが非同期であるため、拒否される。

**[SWS_Can_00287]** Can モジュールは、キャンセルが成功したときに、関数 `CanIf_CancelTxConfirmation` を呼んで、通知を発生させなければならない。（SRS_Can_01133）

**[SWS_Can_00288]** 新しい L-PDU の TX 要求は、通知関数 `CanIf_CancelTxConfirmation` の中で、CanIf モジュールにより繰り返されなければならない。（SRS_Can_01133）

実装上の注意: 順序が関係するストリームでは、送信側は、同じ CAN ID の次の送信要求を、最後の要求が確認された後に限り開始することを、保証しなければならない。

#### 7.5.2 送信データの一貫性

**[SWS_Can_00011]** Can モジュールは、データを上位層のバッファから直接コピーしなければならない。関数呼び出し（`Can_Write`）が戻るまで、バッファを一貫した状態に保つことは、上位層の責任である。（SRS_SPAL_12075、SRS_Can_01059）

### 7.6 L-PDU の受信

**[SWS_Can_00279]** L-PDU の受信時に、Can モジュールは、パラメータ `Mailbox` に ID、`Hoh`、`ControllerId` を、パラメータ `PduInfoPtr` に DLC と L-SDU バッファへのポインタを渡して、RX 通知のコールバック関数 `CanIf_RxIndication` を呼ばなければならない。（SRS_Can_01045）

**[SWS_Can_00423]** 拡張 CAN フレームの場合、Can モジュールは、上位層（CANIF）が、受信した CAN フレームが標準 CAN フレームか拡張 CAN フレームかを知らないため、ID を標準化された形式へ変換しなければならない。拡張 CAN フレームの場合、受信した CAN フレームの ID の MSB を '1' にして、受信した CAN フレームが拡張であることを示す必要がある。

注: CanDrv は、受信したメッセージが従来の CAN フレームか CAN FD フレームかを示さない。

**[SWS_Can_00396]** 対応する HW リソースの RX 割り込みサービスルーチン、またはポーリングモードの場合は関数 `Can_MainFunction_Read` が、コールバック関数 `CanIf_RxIndication` を呼ばなければならない。（SRS_Can_01045）

**[SWS_Can_00060]** CAN によるメモリへのデータの割り当ては、最初に受信される CAN データバイトが配列の要素 0、最後に受信される CAN データバイトが配列の要素 7 になるように定義される。CAN ハードウェアバッファの中の表現が AUTOSAR の定義と異なる場合、Can モジュールは、上位層のために、適合させた SDU バッファを提供しなければならない。（SRS_SPAL_12063）

#### 7.6.1 受信データの一貫性

受信したメッセージの喪失を防ぐため、一部のコントローラは、ハードウェアオブジェクトの集合から作られた FIFO をサポートする。他のコントローラでは、メイン のオブジェクトが使用中のときに代わりを務める、シャドウバッファとして働く、同じ性質を持つ別のハードウェアオブジェクトを、コンフィギュレーションできる。

**[SWS_CAN_00489]** CAN ドライバは、ハードウェア FIFO を実装するコントローラをサポートしなければならない。FIFO のサイズは、`CanHwObjectCount` でコンフィギュレーションされる。

**[SWS_CAN_00490]** ハードウェア FIFO をサポートしないコントローラは、多くの場合、主のハードウェアオブジェクトが使用中のときに、追加のハードウェアオブジェクトが代わりを務ける、シャドウバッファの仕組みを実装する能力を提供する。ハードウェアオブジェクトの数は、`CanHwObjectCount` でコンフィギュレーションされる。

> （図 7-5「同じ HRH の複数のハードウェアオブジェクトへの割り当ての例」: 図。訳なし。選ばれた番号付けは例にすぎない。）

**[SWS_Can_00299]** RX バッファが、新しく受信したメッセージによる上書きから、CAN ハードウェアにより保護（ロック）できない場合、Can モジュールは、受信後に、L-SDU をシャドウバッファへコピーしなければならない。

**[SWS_Can_00300]** CAN ハードウェアがグローバルにアクセスできない場合、Can モジュールは、L-SDU をシャドウバッファへコピーしなければならない。

RX の処理全体（宛先の層、例えば COM へのコピーを含む）は、RX 割り込みのコンテキスト、または `Can_MainFunction_Read` のコンテキストで行われる。

**[SWS_Can_00012]** Can モジュールは、ISR も関数 `Can_MainFunction_Read` も、自分自身に割り込まれないことを保証しなければならない。CAN ハードウェア（またはシャドウ）バッファは、自分自身に割り込まれることのない、ちょうど 1 つの関数の中で、順番に書き込まれ、読み出されるため、常に一貫している。（SRS_Can_01059）

CAN ハードウェアが、受信後に RX ハードウェアオブジェクトをロックするように設定できない場合（ハードウェアの機能）、ハードウェアバッファが、新しく到着したメッセージにより上書きされることがありうる。この場合、CAN コントローラは、ハードウェアがサポートしていれば、「上書き（overwrite）」のイベントを検出する。

CAN ハードウェアが、受信後に RX ハードウェアオブジェクトをロックするように設定できる場合、新しく到着したメッセージを、ハードウェアバッファへ保存できないことがありうる。この場合、CAN コントローラは、ハードウェアがサポートしていれば、「オーバーラン（overrun）」のイベントを検出する。

**[SWS_Can_00395]** Can モジュールの開発エラーの検出が有効な場合、Can モジュールは、「上書き」または「オーバーラン」のイベントの検出の場合に、エラー `CAN_E_DATALOST` を発生させなければならない。

実装のヒント: システム設計者は、メッセージの受信の実行時間（割り込み駆動またはポーリング）が、システムで最も速い可能性のある受信と対応していることを、保証しなければならない。

### 7.7 ウェイクアップの概念

Can モジュールは、CAN トランシーバを介さず、CAN コントローラ自体で検出できるウェイクアップを扱う。取りうるシナリオは 2 つある。割り込みによるウェイクアップと、ポーリングによるウェイクアップである。

割り込みによるウェイクアップでは、ハードウェアがウェイクアップを検出したとき、Can モジュールの ISR が呼ばれる。

**[SWS_Can_00364]** ウェイクアップのイベントの ISR が呼ばれた場合、それは、`EcuM_CheckWakeup` を呼ばなければならない。`EcuM_CheckWakeup` へ渡すパラメータは、コンフィギュレーションパラメータ `CanWakeupSourceRef` で参照されるウェイクアップソースの ID でなければならない。（SRS_BSW_00375、SRS_SPAL_12069、SRS_Can_01054）

ECU State Manager は、その後、MCU を設定し、CanIf を介して Can モジュールを呼び戻し、その結果、`Can_CheckWakeup` が呼ばれる。ウェイクアップのイベントがポーリングで検出される場合、ECU State Manager は、前と同様に、CanIf を介して `Can_CheckWakeup` を周期的に呼ぶ。どちらの場合も、`Can_CheckWakeup` は、Can コントローラが検出したウェイクアップがあったかを検査し、その結果を返す。その後、CAN ドライバは、`EcuM_SetWakeupEvent` を介して、ウェイクアップのイベントを ECU State Manager へ通知する。

誤ったウェイクアップのイベントを防ぐためのウェイクアップの検証は、その後で、Can モジュールの助けなしに、ECU State Manager と CanIf により行われる。

ウェイクアップの仕組みの一般的な説明と、ウェイクアップのシーケンス図は、ECU State Manager の仕様 [7] を参照。

### 7.8 通知の概念

Can モジュールは、CanIf モジュールへ、イベント駆動の通知インタフェースだけを提供する。各通知は、コールバック関数で表される。

**[SWS_Can_00099]** ハードウェアのイベントは、割り込みで、またはハードウェアオブジェクトのステータスフラグのポーリングで、検出してよい。ポーリングに関するコンフィギュレーションの可能性は、ハードウェアに依存し（すなわち、どのイベントをポーリングできるか、どのイベントをポーリングする必要があるか）、この標準では制限されない。（SRS_Can_01132）

**[SWS_Can_00007]** 割り込みをまったく使わない（完全なポーリング）ように、ドライバをコンフィギュレーションできなければならない。（SRS_Can_01062）

Can モジュールがポーリングするものとしないもののコンフィギュレーションは、ドライバの内部のもので、モジュールの外からは見えない。ポーリングは、CAN のメイン関数（`Can_MainFunction_xxx`）の中で行われる。また、ポーリングされたイベントは、適切なコールバック関数で通知される。その場合、呼び出しのコンテキストは ISR ではなく、CAN のメイン関数である。すべてのコールバック関数の実装は、呼び出しのコンテキストが ISR であるかのように行わなければならない。

さらに詳細は、CAN のメイン関数 `Can_MainFunction_Read`、`Can_MainFunction_Write`、`Can_MainFunction_BusOff`、`Can_MainFunction_Wakeup` の説明も参照。

### 7.9 再入可能性の問題

ルーチンが再入可能であるためには、次の条件を満たさなければならない。

- 共有変数を、それぞれが関数の特定のインスタンスに割り当てられていない限り、すべてアトミックに使う。
- 再入不可の関数を呼ばない。
- ハードウェアを、非アトミックに使わない。

送信要求は、CanIf モジュールにより、関数 `CanIf_Transmit` の中で、そのまま転送される。関数 `CanIf_Transmit` は再入可能である。したがって、関数 `Can_Write` は、スレッドセーフ（例えば、ミューテックスを使う）に実装される必要がある。書き込みを再入可能に実行できない場合、さらなる（プリエンプティブな）呼び出しは、`CAN_BUSY` で戻る（例: 異なるハードウェア TX ハンドルへの書き込みは許される、同じ TX ハンドルへの書き込みは許されない）。`CAN_BUSY` の場合、CanIf モジュールは、その要求をキューに入れる（すべてのハードウェアオブジェクトが使用中の場合と同じ動作）。

`Can_EnableCanInterrupts` と `Can_DisableCanInterrupts` は、再入可能な関数の中から呼ばれることがある。したがって、これらの関数も再入可能である必要がある。

その他のサービスは、すべて、再入可能な関数として実装する必要は無い。CAN のメイン関数（すなわち、`Can_MainFunction_Read`）は、自分自身に割り込まれてはならない。したがって、これらの CAN のメイン関数は再入不可である。

### 7.10 パーシャルな通信の模倣（Pretended Networking）

エネルギー効率の最適化は、エネルギーの消費が、燃料の消費、CO2 の排出、ハイブリッド車や電気自動車の航続距離に直接影響するため、すべての自動車の領域で重要性が増している。Pretended Networking の概念は、ECU レベルでのエネルギー削減に高い可能性を持つ。

> （図 7-6「取りうる ICOM の実装」: 図。訳なし。読み取れる内容: (a) ICOM の機能が、既存の通信コントローラを再利用して、ソフトウェアだけで実装される。(b) ICOM が、既存の通信コントローラの機能的なハードウェア拡張である。(c) ICOM が、独自の通信コントローラを持つ、別のハードウェアコンポーネントである。）

これらの機能をサポートするために、インテリジェント通信コントローラ（ICOM）の使用が計画されている（特定のハードウェアの実装は必須ではない）。ECU の機能の一部またはすべてが、例えば車両の状態に基づいて、一時的に必要でない場合、ECU は「Pretended Networking」モードに入れる。このモードでは、MCU および（または）周辺機器が、低消費電力モードに切り替えられる。ICOM と、接続されたトランシーバだけが、動作したままである。ICOM は、ECU が動作を再開する必要があるときに、例えば受信したバスメッセージまたはローカルのイベントを原因とする、ウェイクアップイベントを生成する。

ICOM の実装に応じて、受信したメッセージの ID とペイロードは、完全にハードウェアで評価・フィルタリングされるか、ソフトウェアでのコールバックの仕組みを必要とするか、またはその両方の組み合わせになる。図 7-5 に示すように、ECU の実装は、3 つの取りうる変種に分けられる。最新の通信コントローラを再利用するソフトウェアのアプローチ（a）、最新の通信コントローラの機能的なハードウェア拡張（b）、ウェイクアップの扱いのための、2 つ目の拡張された通信コントローラを持つハードウェアの変種（c）である。すべての変種と ICOM の実装は、Pretended Networking でサポートされなければならない。

ハードウェアの実装に応じて、ICOM は、メッセージを送信することもできる。ICOM を使って、例えば状態メッセージを送り続けることで、そのメッセージに依存する他のノードは、Pretended Networking モードの ECU の影響を受けない。

さらに、Pretended Networking は、ウェイクアップの応答時間、すなわち、ウェイクアップのイベントから、ECU の有効な動作までの時間を、減らすことを目指す。Pretended Networking モードが有効な間に、ICOM を使って関連するメッセージを保存することで、アプリケーションは、動作を再開した直後に、最後の有効な信号値へアクセスできる。したがって、ECU は、ウェイクアップの後、ユーザの要求に直ちに応答でき、対応するメッセージが再び受信されるまで待つ必要が無い。

#### 7.10.1 Pretended Networking のモードの扱いのサポート

**[SWS_CAN_00497]** CAN ドライバは、CAN コントローラの初期化の後に、Pretended Networking を無効にしなければならない。

Pretended Networking の有効化:

**[SWS_CAN_00462]** Pretended Networking は、0 より大きいコンフィギュレーション ID で `Can_SetIcomConfiguration` を呼ぶことで、有効にされなければならない。

**[SWS_CAN_00463]** 新しいコンフィギュレーションを CAN コントローラと ICOM に適用する場合、コンフィギュレーションパラメータを検査するのは、CAN ドライバの責任である。

**[SWS_CAN_00464]** CAN コントローラ（ICOM を含む）の再設定を行うのは、CAN ドライバの責任である。

**[SWS_CAN_00465]** Pretended Networking の有効化が成功したかを CAN Interface へ通知するのは、CAN ドライバの責任である。

**[SWS_CAN_00466]** Pretended Networking の有効化が成功した場合、CAN ドライバは、ICOM が有効になったという情報を保存しなければならない。

**[SWS_CAN_00467]** 有効化が成功した場合、`CanIf_CurrentIcomConfiguration` は、パラメータ `Error` を `ICOM_SWITCH_E_OK` に設定して呼ばれなければならない。有効化が成功しなかった場合、`CanIf_CurrentIcomConfiguration` は、パラメータ `Error` を `ICOM_SWITCH_E_FAILED` に設定して呼ばれなければならない。

**[SWS_CAN_00468]** ハードウェアのサポート無しに Pretended Networking が有効にされた場合（ソフトウェアの実装 ― 変種 a）、CAN ドライバは、ウェイクアップに関係しないメッセージの受信割り込みを無効にしなければならない（ウェイクアップの原因としてコンフィギュレーションされたメッセージだけが、ウェイクアップ割り込みを生成する）。

**[SWS_CAN_00469]** `CanIcomVariant` が `CAN_ICOM_VARIANT_HW` に設定された状態で Pretended Networking が有効にされた場合（図 7-6 の実装の変種 b と c）、CAN ドライバは、すべての受信割り込みを無効にしなければならない。

**[SWS_CAN_00470]** Pretended Networking が有効にされた場合、CAN ドライバは、送信メッセージの割り込みを無効にしなければならない。

**[SWS_CAN_00498]** CAN ドライバは、CAN コントローラが `SetControllerMode(CAN_T_START)` で開始される前に、Pretended Networking を無効にしなければならない。

Pretended Networking の無効化:

**[SWS_CAN_00471]** Pretended Networking は、コンフィギュレーション ID = 0 で `Can_SetIcomConfiguration` を呼ぶことで、無効にされなければならない。

**[SWS_CAN_00472]** Pretended Networking が無効にされた場合、CAN ドライバは、通常のコンフィギュレーションでコンフィギュレーションされた、すべての受信メッセージの割り込みを有効にしなければならない。

**[SWS_CAN_00473]** Pretended Networking が無効にされた場合、CAN ドライバは、送信メッセージの割り込みを有効にしなければならない。

**[SWS_CAN_00474]** CAN ドライバは、コンフィギュレーションの切り替えについて、`CanIf_CurrentIcomConfiguration` を呼んで CanIf へ通知しなければならない。エラーのパラメータは、無効化が成功した場合は `ICOM_SWITCH_E_OK`、そうでなければ `ICOM_SWITCH_E_FAILED` に設定される。

**[SWS_CAN_00475]** Can モジュールの開発エラーの検出が有効な場合、関数 `Can_SetIcomConfiguration` は、無効な `ConfigurationId` で呼ばれたとき、開発エラー `CAN_E_ICOM_CONFIG_INVALID` を報告しなければならない。

**[SWS_CAN_00499]** CAN ドライバは、CAN コントローラが `SetControllerMode(CAN_T_STOP)` で停止される前に、Pretended Networking を無効にしなければならない。

#### 7.10.2 メッセージの自律的な送受信のサポート

**[SWS_CAN_00477]** Pretended Networking のモードでのメッセージの自律的な送信は、追加の ICOM ハードウェアが利用できる場合に限り、サポートされなければならない。コンフィギュレーションパラメータが、ハードウェアのサポートがあるかを定義する（`CanIcomVariant` を参照）。

**[SWS_CAN_00478]** ICOM がソフトウェアで実装されている場合、Pretended Networking のモードでメッセージを送信してはならない。

**[SWS_CAN_00479]** CanDriver は、Pretended Networking のモードの間に受信したすべてのメッセージを、CanIf へ転送しなければならない。

Can モジュールは、Can モジュールに定義されたプロダクションエラーコードが無いため、Diagnostic Event Manager を呼ばない。

#### 7.11.3 戻り値

`CAN_BUSY` は、関数 `Can_Write` の戻り値で報告される。CanIf モジュールは、CanIf モジュールに規定されたシーケンス図に従って反応する。`CAN_NOT_OK` は、スリープモードへの遷移の間のウェイクアップの場合に、戻り値で報告される。バスオフとウェイクアップのイベントは、通知のコールバック関数で転送される。

### 7.12 CAN FD のサポート

性能上の理由から、一部の CAN コントローラは、CAN FD と呼ばれる、可変データレートの機能を使える（「CAN with Flexible Data-Rate」の仕様を参照）。アービトレーションの段階で示すことで、ペイロードと CRC の間は、より高いボーレートへ切り替えられる。この 2 つ目のボーレートは、`CanControllerBaudrateConfig` を `CanControllerFdBaudrateConfig` で拡張して、コンフィギュレーションする必要がある。CAN FD のコンフィギュレーション（`CanControllerFdBaudrateConfig` を参照）を持つボーレートが有効な場合、このコントローラで CAN FD の機能が有効になる。指定された 2 つ目のボーレートは、ビットレートの切り替え（BRS）を伴う CAN FD のフレームの受信をサポートするために必要である。2 つ目のボーレートを送信に使うかどうかは、コンフィギュレーションパラメータ `CanControllerTxBitRateSwitch`（`CanControllerFdBaudrateConfig` を参照）に依存する。

ただし、例えば CAN の選択的ウェイクアップを容易にするために、CAN-FD のメッセージをサポートするネットワークで、従来の CAN 2.0 のメッセージを送信する必要がある場合がある。これらの場合、従来の CAN メッセージを CAN-FD のメッセージと交互に送信することをサポートする必要がある。これは、フレームのレベルで、`Can_Write` の間に渡される CanId の上位 2 ビット（`Can_IdType`、[SWS_Can_00416] を参照）を使って、どの種類のフレームを使うかを示すことで実現できる。さらに、`Can_SetBaudrate()` を使って、CAN FD でないボーレートへ切り替えることもでき、これにより、CanDrv は、CanId パラメータの CAN FD フラグを無視する。

（SRS_Can_01049）

### 8.4 コールバック通知

この章は、Can モジュールが下位層のモジュールへ提供するすべての関数を列挙する。Can モジュールの下位層のモジュールは、SPI モジュールである。MCAL の一部である SPI モジュールは、マイクロコントローラと外付けの CAN コントローラの間でデータを交換するために使われることがある。

Can モジュールは、コールバック関数を提供しない。外付けの CAN コントローラへアクセスするために、同期の MCAL API だけが使われることがある。

#### 8.4.1 コールアウト関数

AUTOSAR の CAN モジュールは、L-PDU を受信するたびの、オプションの L-PDU コールアウトをサポートする。

**[SWS_Can_00443]** L-PDU コールアウトの API は、次のように定義されなければならない。

```c
FUNC(boolean, COM_APPL_CODE) <LPDU_CalloutName>
(
    uint8       Hrh,
    Can_IdType  CanId,
    uint8       CanDlc,
    const uint8 *CanSduPtr
)
```

ここで、`<LPDU_CalloutName>` は、コンフィギュレーションできる、具体的な L-PDU コールアウトの名前で置き換えなければならない（`SWS_Can_00434_Conf` を参照）。

**[SWS_Can_00444]** L-PDU コールアウトが `false` を返した場合、L-PDU は、それ以上処理されてはならない。

#### 8.4.2 ウェイクアップ通知の有効化・無効化

**[SWS_Can_00445]** Can ドライバは、ウェイクアップのイベントの通知を有効・無効にするために、Icu ドライバが提供する次の API を使わなければならない。

- `Icu_EnableNotification`
- `Icu_DisableNotification`

**[SWS_Can_00446]** 「外付けの」Can コントローラが `SLEEP` の状態（`CANIF_CS_SLEEP`）へ遷移したとき、`Icu_EnableNotification` が呼ばれなければならない。

**[SWS_Can_00447]** 「外付けの」Can コントローラが `STOPPED` の状態（`CANIF_CS_STOPPED`）へ遷移したとき、`Icu_DisableNotification` が呼ばれなければならない。

#### 8.6.3 コンフィギュレーションできるインタフェース

Can モジュールには、コンフィギュレーションできる対象は無い。Can モジュールは、常に CanIf モジュールへ報告する。

### 8.7 Pretended Networking をサポートする API

#### 8.7.1.1 Can_SetIcomConfiguration

| 項目 | 内容 |
|---|---|
| サービス名 | `Can_SetIcomConfiguration` |
| 構文 | `Std_ReturnType Can_SetIcomConfiguration(uint8 Controller, IcomConfigIdType ConfigurationId)` |
| サービス ID [hex] | 0xf |
| 同期／非同期 | 非同期 |
| 再入可能性 | 異なるコントローラ Id でだけ再入可能 |
| 入力パラメータ | `Controller`: 状態を変更する CAN コントローラ。<br>`ConfigurationId`: 要求されるコンフィギュレーション |
| 入出力パラメータ | なし |
| 出力パラメータ | なし |
| 戻り値 | `Std_ReturnType`<br>`E_OK`: CAN ドライバが、有効なコンフィギュレーション ID で、コンフィギュレーションを設定できた。<br>`E_NOT_OK`: CAN ドライバが、有効なコンフィギュレーション ID で、コンフィギュレーションを設定できなかった。 |
| 説明 | このサービスは、CAN コントローラの Icom コンフィギュレーションを、要求されたものへ変更する。 |

**[SWS_CAN_00480]** インタフェース `Can_SetIcomConfiguration` は、Pretended Networking を有効にし、指定されたコントローラについて、要求された ICOM コンフィギュレーションをロードしなければならない。

**[SWS_CAN_00481]** 関数 `Can_SetIcomConfiguration` は、`ConfigurationId` で指定された ICOM のコンフィギュレーションパラメータで、コントローラを再設定しなければならない。

**[SWS_CAN_00482]** メッセージオブジェクトの rx と tx の割り込みは、コントローラがサポートしている場合、有効または無効にしなければならない。

**[SWS_CAN_00483]** ICOM がハードウェアで実装されている場合、ICOM のハードウェアは、有効または無効にしなければならない。

**[SWS_CAN_00495]** `Can_SetIcomConfiguration()` は、コンフィギュレーションパラメータ `CAN_PUBLIC_ICOM_SUPPORT` で、プリコンパイル時に ON/OFF をコンフィギュレーションできなければならない。

> **学習メモ（原文でなく訳者の解釈）**: このプロジェクトの Can との対応を見るときの手がかり。
> - コントローラの状態遷移は、`UNINIT` →（`Can_Init`）→ `STOPPED` ⇄ `STARTED`（`CAN_T_START`／`CAN_T_STOP`）、`STOPPED` ⇄ `SLEEP`（`CAN_T_SLEEP`／`CAN_T_WAKEUP`）。バスオフは `STARTED` → `STOPPED` へ遷移させ、自動回復は無効にする（[SWS_Can_00272]〜[SWS_Can_00274]）。
> - `Can_Write` は非同期ではなく、ブロックせず（[SWS_Can_00275]）、空きの送信オブジェクトが無ければ `CAN_BUSY` を返す。CanIf の送信バッファリングは、この `CAN_BUSY` を受けて働く。
> - 受信のオーバーラン／上書きは、開発エラーの検出が有効なら `CAN_E_DATALOST` で報告する（[SWS_Can_00395]）。
> - `Can_SetBaudrate` は、再初期化が必要なら、`STOPPED` でなければ `E_NOT_OK` を返し、`CAN_E_TRANSITION` を発生させる（[SWS_Can_00256]）。
